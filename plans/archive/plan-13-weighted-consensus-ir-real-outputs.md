## 1. Purpose

This plan runs and hardens the existing weighted consensus path on real Plan 10, Plan 11 and Plan 12 artefacts.

The repository already has the consensus stack:

```text
src/pdf2md/consensus/factory.py
src/pdf2md/consensus/scoring.py
src/pdf2md/consensus/io.py
src/pdf2md/consensus/grouping.py
src/pdf2md/consensus/reporting.py
tools/build_consensus.py
```

Plan 13 must reuse this stack.

The core question is:

```text
Can the existing consensus path build valid, explainable ConsensusIR from real multi-backend outputs using Plan 12 priors?
```

Plan 13 must prove:

```text
ConsensusIR can be built from real connector outputs.
Plan 12 priors are loaded and used.
Confidence is traceable to backend evidence and priors.
Conflicts are explicit.
Provenance is preserved.
The result can be inspected against ground truth and individual backend outputs.
```

Plan 13 does not build a full automated comparative evaluation framework. That belongs to Plan 16, where the end-to-end runner and MVP corpus evaluation are assessed. In Plan 13, comparison against individual backends and ground truth is a basic inspection and quality checkpoint, not a full evaluation product.

Consensus outcome taxonomy:

accepted:
Candidate selected into ConsensusIR with sufficient confidence.

rejected:
Candidate rejected because stronger weighted evidence supports an alternative.

uncertain:
Candidate cannot be resolved confidently and is preserved as low-confidence or conflict evidence.

conflict:
Multiple backend candidates disagree materially.

missing_upstream_candidate:
A candidate type, such as embedded-text or tagged-PDF evidence, is not available because upstream extraction did not provide it.

Quality inspection outcome taxonomy:

appears_better_than_backends:
Manual/basic inspection suggests consensus improves over individual backend outputs.

appears_equivalent_to_best_backend:
Consensus is comparable to the best backend.

appears_worse_than_best_backend:
Consensus appears worse than the best backend. This is information, not automatically a repository defect.

inconclusive:
Ground truth or backend support is insufficient for a stable judgement.

diagnostic_only:
Plan 12 priors or Plan 10/11 outputs are insufficient for trusted consensus, but a diagnostic run was approved by the human.

## 8. Test matrix and failure classification

Agent automated test matrix:

```bash

```

Human verification test matrix:

```text
H1 input readiness and existing CLI gate
H2 one-document ConsensusIR build and conflict inspection
H3 basic quality inspection against backends and ground truth
```

Plan-level statuses:

consensus_ready:
Plan 12 priors and Plan 10/11 outputs are available and aligned.

consensus_blocked:
Required priors or inputs are missing or unsafe.

diagnostic_only:
Human permits a diagnostic run despite insufficient priors or reduced backend support.

Per-document consensus statuses:

consensus_built:
ConsensusIR validates for the document.

consensus_failed:
Consensus building fails.

conflicts_unresolved:
ConsensusIR builds but important conflicts remain unresolved.

low_confidence:
ConsensusIR builds but confidence is below threshold for important regions.

insufficient_backend_diversity:
Too few independent backend outputs exist.

Quality inspection statuses:

appears_better_than_backends:
Manual/basic inspection suggests consensus improves over individual backend outputs.

appears_equivalent_to_best_backend:
Consensus is comparable to the best backend.

appears_worse_than_best_backend:
Consensus appears worse than the best backend. This is information, not automatically a repository defect.

inconclusive:
Ground truth or backend support is insufficient for stable judgement.

Failure classes:

repository_defect:
Existing consensus builder, reporting, tests or CLI integration are wrong.

missing_priors:
Plan 12 priors are missing.

unsafe_priors:
Plan 12 priors exist but are underpowered, no_samples only, or explicitly unsafe for consensus.

missing_backend_outputs:
Plan 10/11 backend outputs are missing.

backend_name_mismatch:
Backend names do not align across priors and connector outputs.

consensus_schema_failure:
ConsensusIR fails schema validation.

provenance_failure:
Consensus output lacks backend provenance or raw evidence traceability.

conflict_reporting_failure:
Conflicts are silently dropped or not reported.

scope_violation:
Plan 13 performs extraction, calibration, linking, export or end-to-end work.

human_procedure_error:
Human ran the wrong command, used wrong roots or inspected stale outputs.

test_expectation_wrong:
The test or checkpoint expectation is inconsistent with the plan or repository contract.

Failure handling:

If failure_class is repository_defect:
The agent must fix the implementation or report a blocker.

If failure_class is missing_priors:
Plan 12 must be completed or artefacts provided.

If failure_class is unsafe_priors:
Human may approve diagnostic mode or block Plan 13.

If failure_class is missing_backend_outputs:
Human must provide artefacts or backend is excluded with explicit risk.

If failure_class is backend_name_mismatch:
Fix input mapping or report blocker.

If failure_class is consensus_schema_failure:
Fix consensus construction or model usage.

If failure_class is provenance_failure:
Fix consensus explanation/provenance before human_verified.

If failure_class is conflict_reporting_failure:
Fix conflict reporting before human_verified.

If failure_class is scope_violation:
Reject the plan output and revert or revise.

If failure_class is human_procedure_error:
Human checkpoint must be rerun correctly.

If failure_class is test_expectation_wrong:
The plan must be revised by a human before continuing.

If consensus does not improve over the best backend:
Record it as quality inspection information, not as automatic repository_defect. Diagnose likely cause and let the human decide whether Plan 14 can proceed.

## 9. Checkpoints, push policy and hand-off

Checkpoint C0: Plan ready

Required before agent starts:

```text
status is active
Plan 12 status is human_verified or human explicitly approves drafting only
scope is clear
file whitelist is complete
forbidden files are listed
dependencies are declared
agent tasks are listed
automated tests are listed
human verification checkpoints are listed
next plan is identified
```

Checkpoint C1: Agent implementation complete

Required before human verification:

```text
all agent tasks attempted
all required automated tests run
no forbidden files modified without human amendment
no undeclared dependencies used
existing build_consensus.py path used
consensus output produced or blocker reported
agent report completed
status set to agent_complete or human_verification_required
```

Checkpoint C2: Human verification complete

Required before merge or milestone completion:

```text
H1 input readiness passed
H2 one-document ConsensusIR build passed
H3 basic quality inspection completed
all expected output files produced or failures classified
non-improvement, if observed, was diagnosed
human verification report completed
status set to human_verified by a human
```

Checkpoint C3: Plan finished and promoted

Required before promotion:

```text
status is human_verified
Plan 13 is archived after completion
history.md summary is prepared or updated
Plan 14 exists as next_plan.md or approved prepared plan
Plan 14 may be promoted to current_plan.md only after Plan 13 is finished
ROADMAP.md progress is updated only if explicitly approved by the human
```

Push and PR policy:

```text
The agent may push an implementation branch if the plan allows it.
The agent may open a draft PR if the plan allows it.
The agent must not merge to main.
The agent must not direct-push to main unless the human explicitly authorises it for that specific change.
```

Human verification must pass before:

```text
merging to main
marking the plan finished
promoting next_plan.md
updating ROADMAP.md progress
declaring the milestone achieved
```

Hand-off procedure after human verification:

1. Archive current_plan.md as:

```text
plans/archive/plan-13-weighted-consensus-ir-real-outputs.md
```

2. Append a milestone summary to history.md.
3. Promote Plan 14 to current_plan.md.
4. Create a new next_plan.md from PLAN_TEMPLATE.md or from an approved prepared plan.
5. Record the commit SHA or PR number.
6. Record the human verification evidence.
7. Confirm whether ROADMAP.md progress should change.
