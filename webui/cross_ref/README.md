# pdf2md — semantic + docling viewer

Static, build-step-free viewer for the `CrossReferenceGraph` (semantic
side) and `DoclingDocument` (structural side) of the example PDFs.

The page loads [D3 v7](https://cdn.jsdelivr.net/npm/d3@7) from a CDN at
runtime — no `package.json`, no React, no Vite. Serve with any static
file server.

## Quick start

```bash
python -m http.server --directory webui/cross_ref 8080
# → open http://localhost:8080/
```

Use the dropdowns at the top to pick:

- **Example** — `example01` (1410.8140, physics, no References heading)
  or `example02` (2401.12345, math/CS paper with theorems).
- **Semantic backend** — `regex` / `grobid` / `vlm_v4`. Each detects
  cross-reference markers in a different way.
- **OCR candidates** — pick an OCR backend (`deepseek` / `mineru` /
  `paddleocr`) to enable the OCR → resolver bridge. Resolved edges
  show as solid green lines, unresolved as dashed red. Pick "none"
  for the raw marker view.

The right side panel has three tabs:

- **Stats** — marker counts by type, resolution rate, backend
  versions.
- **Docling structure** — a tree view of the OCR-extracted document
  structure (page → text/figure/table items), produced by the docling
  export stage of the pipeline.
- **Markers** — a flat list of every detected marker with its
  resolved target.

## Recommended viewing combinations

| Example | Best semantic backend | Best OCR | Resolution rate |
|---|---|---|---|
| example01 (physics) | `vlm_v4` | `deepseek` | 23.5% (4/17) |
| example02 (math/CS) | `grobid` | `deepseek` | **82.3%** (116/141) |

For the math example, `grobid` parses the bibliography section
accurately (the paper has an explicit "References" heading), so the
OCR → resolver bridge can pair each `[N]` citation marker with its
bibliography entity.

For the physics example, there is no "References" heading — GROBID
still detects all `[N]` markers, but the OCR side classifies the
bibliography entries as ``footnote`` rather than ``reference_item``,
so the bridge resolves only the figure / caption pairs. This is a
known OCR-side limitation, not a viewer bug.

## How the data is produced

The `data/` directory is regenerated by:

```bash
# 1. Run the comprehensive benchmark (writes /tmp/bench_out/...).
PYTHONPATH=src conda run -n pdf2md python /tmp/semantic_benchmark.py

# 2. Render D3-ready graphs + resolve against OCR entities.
PYTHONPATH=src conda run -n pdf2md python /tmp/produce_resolved_graphs.py

# 3. (manual) copy the precomputed VL2 outputs + docling JSONs into
#    webui/cross_ref/data/<example>/.
```

The benchmark and resolver scripts live under `/tmp/` because they
operate on `pdf2md/.tmp/papers_run/<example>/` cached pipeline outputs
— they're development-time tooling, not part of the repository's
public surface.

## Schema

`<semantic>__resolved_with__<ocr>.json` follows
`pdf2md.semantic.graph_export.GraphExport`:

```json
{
  "schema_version": "1.0.0",
  "document_id": "example02/grobid+deepseek",
  "nodes": [...],
  "edges": [
    {
      "source": "marker:0:#/document:[2]",
      "target": "ent:deepseek:2401.12345:reference_item:42",
      "marker_type": "bibliography",
      "label": "[2]",
      "resolved": true
    }
  ],
  "metadata": {
    "doc_hash": "sha256:...",
    "total_markers": 141,
    "resolved_count": 116,
    "unresolved_count": 25,
    "backend_versions": {"grobid": "0.1.0"}
  }
}
```
